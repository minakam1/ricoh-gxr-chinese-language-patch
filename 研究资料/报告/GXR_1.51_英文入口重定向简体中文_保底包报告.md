# 【真机失败，请勿刷写】GXR 1.51 English 入口重定向简体中文实验包

日期：2026-07-30
状态：**真机刷写后菜单出现乱码，方案已判定失败**

## 真机结果

2026-07-30 在 GXR 真机上完成刷写后，相机能够启动和显示菜单框架，
但菜单文字呈现混合拉丁字形、假名和符号的乱码；切换到日语也未恢复。

这说明静态资源重定向虽然通过了升级校验，却没有让程序进入简体中文所需的
语言编号、字体、字形映射和资源初始化路径。中文资源还明显大于英文资源，
因此也不能排除英文路径的缓冲区或工作区尺寸不适配。

**结论：不要再使用本实验包。应立即用官方原版 1.51 的全部 29 个文件恢复。**

## 结论

已基于理光官方原版 `gxr-151.zip` 生成一个独立实验包。它不修改程序代码，
只把七个资源容器中的：

```text
com_main_eng.res
```

索引重定向到同一文件内原本存在的：

```text
com_main_chinsimpl.res
```

预期行为是：

- 语言菜单仍只显示 `日本語 / English`；
- 选择 `English` 时实际加载简体中文资源；
- 原始简体中文资源实体、字体和程序均不修改。

这不是地区解锁，也不会让语言菜单新增 “简体中文” 项目。

## 校验算法

升级器中的校验核心函数位于：

```text
运行地址 0x20087AF0
```

算法核心是对 `0x200` 字节头部之后的 payload 做加权字节和：

```text
checksum = Σ byte[i] × (((phase + i) mod 6) + 2) mod 2^32
```

本实验包修改的 `launch4` 资源容器使用 `phase = 0`，即循环权重：

```text
2, 3, 4, 5, 6, 7
```

后续复核发现，不同容器类型的初始相位并不统一：`launch3` 多段程序容器
同样使用 `phase = 0`，而部分固定地址镜像使用装载地址相位。因此此前
“统一按装载地址、全部 29 个文件均匹配”的表述不准确。七个被修改的
`launch4` 文件均已按其真实 `phase = 0` 校验通过，不影响本实验包的
静态校验结论。

修改后的校验：

```text
ilaunch4:
  0x436AFC97 -> 0x436AFB49

其余六个模块资源容器:
  0x0AAA7C7F -> 0x0AAA8061
```

没有绕过校验，也没有修改升级器。

## 已知风险与未知项

已验证的是二进制结构、资源重定向、文件差异和升级文件校验。

尚未验证：

1. 已安装 1.51 的机身是否允许再次刷写同版本；
2. 升级器是否还有尚未触发的外部策略检查；
3. 固件启动后是否还有语言编号与资源内容一致性检查；
4. 所有拍摄、回放及模块专用页面是否都正常加载中文；
5. 官方同版本包能否在异常情况下用于恢复；
6. 真机刷写失败后的硬件恢复手段。

因此它只能称为实验保底包，不能称为安全升级包。

## 建议的真机验证顺序

第一步只验证升级器识别，不确认写入：

1. 使用相机格式化的 SD 卡；
2. 复制 `SD_ROOT` 中全部 29 个文件到卡根目录；
3. 满电、关机；

5. 观察是否正常进入升级确认及文件检查；
6. 此阶段选择 `No` 退出。

只有确认升级器识别文件、机身和模块均正确后，再单独决定是否执行真实刷写。
