# Ricoh GXR 1.51 固件逆向初步报告

分析对象：官方 `gxr-151.zip`，全程只读，没有生成可刷写修改文件。

## 结论

1. **简体中文和繁体中文程序资源完整存在。** 机身主程序 `ilaunch3` 有一张明确的 11 语言指针表；机身资源包 `ilaunch4` 也含对应资源实体。因此日版机身仅显示日语/英语，不是因为缺字库或缺菜单翻译。
2. **没有在升级包中发现“日版程序”和“中文版程序”两套不同机身固件。** 当前证据更支持：语言可用范围由机身或相机模块的持久化调整数据、地区参数控制。
3. **用户所说“从中文模块读取配置到机身”的办法与固件结构高度吻合。** 固件同时包含机身/模块调试壳切换、调整命令、配置备份恢复以及模块间控制通道。
4. **暂未定位到地区/语言参数的确切编号或字节。** 仅靠公开升级包不能直接看到模块 EEPROM 的出厂数据。
5. **不建议现在修改 `ilaunch3/4` 刷入。** 固件头有自定义校验，算法尚未确认；即使绕过，也不是最干净的改区方法。

## 固件格式

- 机身文件标识：`R_NS1_REFLECTOR`
- 更新完成标识：`R_NS1_UPDATED!!!`
- 版本字节：`1.51`
- 头长度：`0x200`
- CPU 主架构：Renesas M32R（由异常寄存器名、Renesas 字符串及代码结构判断）
- `ilaunch3` 被拆为 16 个装载段；完整地址表见 CSV。
- 固件头 `0x16C` 有 32 位校验值。CRC32、Adler32、普通字节和、32 位字和均不匹配，属于自定义算法或带特殊范围/初值的校验。

## 配置和维修通道证据

机身和模块程序均保留：

- `Change shell control on [Lens Unit]`
- `Change shell control on [Body Unit]`
- `--- Backup restore`
- `/CONFIG.TST`
- `/CONFIG.BAK`
- `/SCINST.TST`
- `adjcom` / `adjcom2`
- `*** send adj command ...`
- `SysUnit Debug Commands`

脚本解释器支持按键、拨轮、跳转、变量、调整命令以及安装/卸载脚本。配置备份代码会生成类似 `CFGTxxxx.TST`、`CFGBxxxx.BAK` 的文件，并使用 `Z4000`、`Z4100`、`Z4200`、`Z5000`、`ZB4xx`、`Z51xx` 等调整协议命令。

## `INCOPY.KEY` 线索

只有机身主程序 `ilaunch3` 找到：

- `/ATA1/DBGMODE.key`：文件偏移 `0x33256E`
- `/ATA1/INCOPY.KEY`：文件偏移 `0x332608`，运行地址 `0x2037D408`
- `/IROM/LAUNCHA`
- `/IROM/DMY.bin`

这组字符串位于固件升级、初始化和兼容性处理代码附近。`INCOPY.KEY` 很可能触发“向机身内部复制”的维修流程，但目前尚未证明其复制源、目标和数据范围。**不要把空的 `INCOPY.KEY` 放进 SD 卡试机**，它可能涉及内部 ROM 或配置区覆盖。

## 最可能的正确路线

1. 用维修/调试方式从同一台机身导出改中文前的 `CONFIG.TST` 或调整区数据。
2. 使用中文地区模块执行已知的“读取配置到机身”操作。
3. 再导出一次配置。
4. 对两份数据逐字段比较，排除日期、计数器、序列号和校准项。
5. 通过反复切换验证候选字段，最终只修改地区/语言字段及其校验。

与直接克隆模块全部配置相比，这条路线可以避免覆盖传感器坏点、白平衡、对焦、镜头畸变、序列号等模块专属校准数据。

- “读取配置到机身”操作的准确菜单入口、按键步骤和屏幕提示。

你说得对。拆包后的准确结论是：

**这不是完整机内文件系统，但也不是差分补丁。它是一组“各固件组件的完整替换映像”。其中 `launch4` 确实能拆出完整的机内资源文件。**

具体如下。

### `ilaunch4`：完整资源文件包

这个文件可以完整解析。去掉 `0x200` 字节升级头后：

* 开头 4 字节指向资源目录；
* 中间连续存放资源文件内容；
* 末尾是 68 条目录记录；
* 每条记录是：24 字节文件名＋4 字节偏移＋4 字节长度。

数据区域由这些资源完整覆盖，只夹有总计 **34 字节的四字节对齐填充**，没有大块未知数据。

能拆出 68 个独立资源文件，包括：

```text
com_main_jpn.res
com_main_eng.res
com_main_chinsimpl.res
com_main_chintrad.res
bmp_data_VGA.res
font_ctbl_00.res ～ font_ctbl_31.res
half_16.rex
……
```

所以在资源这一部分，答案是：

> **是，`ilaunch4` 装的是完整资源文件，不是补丁碎片。**

镜头模块的 `j/k/n/q/l06/l08 ...4` 同样是这种格式，但只有 22 个资源文件。

### `ilaunch3`：完整主程序映像，但不是文件系统

`ilaunch3` 也不是差分补丁。它的升级头中有 **16 条装载段记录**，每条记录明确给出：

```text
固件内源偏移
运行装载地址
已初始化数据长度
BSS 地址
BSS 长度
```

例如机身主程序会被装载到多段地址：

```text
0x2004B000
0x20055000
0x200D8C00
……
0x203C7C00
0x05000C00
```

这相当于一个专用格式的可执行程序映像，类似 ELF 中的多个 `LOAD` 段，但没有 ELF 外壳。

所以：

> **`ilaunch3` 是完整的主程序组件，但不是把 `/IROM` 目录逐文件打包出来的镜像。**

### `ilaunch0`：完整 Monitor/启动维护程序

它去掉升级头后是一个连续的 `0x8CA28` 字节映像，目标地址为：

```text
0x27E00000
```

里面明确存在：

```text
Boot & Monitor
Backup prog blk
Adjust data blk
Adjust Kiz blk
Main prog blk
Extend data blk
ROM MAP
```

以及 ROM 擦除、转储、内存读写、升级、备份程序启动等命令。

因此它是完整的 Monitor/维护程序组件，而不是整个内部 ROM。它自己还会访问其他 ROM 区域。

### `ilaunch8`：寄存器写入脚本

它不是二进制文件系统镜像，而是近一万行文本命令：

```text
X12C0
UEEF1
V0002
W0151
V000C
W3302
……
UEE00
```

基本结构是：

* `Vxxxx`：设置地址；
* `Wxxxx`：写入数值；
* `Uxxxx`、`Xxxxx`：控制命令。

里面还有日文注释：

```text
#奇数アドレスと偶数アドレスの運用は同じにしてください！
```

即“奇数地址和偶数地址请采用相同方式处理”。

所以它是完整的某项硬件寄存器/控制器初始化数据脚本。

### 缺失的机内内容

主程序明确引用了这些真实机内或维修文件：

```text
/IROM/BADJRAM.DAT
/IROM/BKIZRAM.DAT
/IROM/BKIZROM.DAT
/IROM/DCTRACE.LOG
/IROM/RADJ
/CONFIG.TST
/CONFIG.BAK
/ATA1/IROM.DAT
/ATA1/IROM2.DAT
```

但它们**没有作为资源条目或独立文件包含在升级包里**。升级包里只有程序代码会读取、写入或导出它们。

尤其是：

```text
BADJRAM.DAT
BKIZRAM.DAT
BKIZROM.DAT
```

从名称和相关代码看，正是机身调整数据、坏点或个体校准数据所在区域。这些内容是每台机器实际生成和保存的，不可能由通用升级包统一提供。

所以最终应该这样表述：

| 内容              | 是否完整        |
| --------------- | ----------- |
| 主程序组件           | 是，完整替换映像    |
| Monitor 程序      | 是，完整替换映像    |
| 菜单、字库、图片资源文件    | 是，可以逐文件完整拆出 |
| 硬件寄存器写入表        | 是，完整脚本      |
| 整个 `/IROM` 文件系统 | 否           |
| 机身 NVRAM/EEPROM | 否           |
| 地区及语言配置         | 没有直接包含      |
| 个体校准和坏点数据       | 没有包含        |
| Boot ROM 全量转储   | 没有包含        |

我之前简单说“不是完整机内文件”不够准确。**准确说法是：它包含完整的通用固件组件和完整资源文件，但不包含机器当前内部存储中的全部文件及个体配置。**

这也意味着下一步可以直接从 `ilaunch0` 的 ROM dump、`IROM.DAT`、`BKIZROM.DAT` 相关代码入手，研究如何把机内地区配置只读导出来。
