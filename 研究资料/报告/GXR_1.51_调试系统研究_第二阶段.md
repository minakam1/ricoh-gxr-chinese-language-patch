# Ricoh GXR 1.51 调试系统研究：第二阶段

分析对象：官方 `gxr-151.zip` 中的机身主程序 `ilaunch3`。

本阶段从字符串扫描推进到 M32R 指令级交叉引用。所有结论来自静态分析，未在真机触发任何调试或写入流程。

## 一、`INCOPY.KEY` 已还原到代码级

路径字符串：

- 文件偏移：`0x332608`
- 运行地址：`0x2037D408`
- 引用函数：`0x2036E104`

该函数的实际逻辑为：

1. 打开 `/ATA1/INCOPY.KEY`；
2. 最多读取 32 字节到栈缓冲区；
3. 关闭文件；
4. 只有读取返回值**恰好等于 16**时返回成功；
5. 否则返回 `-1`。

该校验函数中没有比较缓冲区内容。因此从这一个函数看，关键是文件长度为 16 字节，而不是某个口令内容。但不能排除后续流程还使用其他状态或校验。

### 后续控制流

`INCOPY.KEY` 成功后调用 `0x2036E17C`。该函数依次调用三个内部子系统：

- `0x202E4F44(12)`
- `0x2025DB40(2)`
- `0x20111C3C()`

这些调用表现为模式切换、状态提交和重启/转场类操作，但名称尚未完全恢复。

更外层的启动状态机位于 `0x2036E34C` 附近。`INCOPY.KEY` 只有在以下条件之一成立时才会被检查：

- 启动状态位 `0x00000002` 已置位；或
- 一个内部启动状态函数返回值等于 `8`。

所以它不是普通开机时无条件生效的标记文件。

**风险判断：高。** 目前绝不能因为知道“16 字节”就直接放文件试机。它通过后不是进入一个可见菜单，而是跳入尚未完全命名的内部模式切换。

## 二、`DBGMODE.key` 与 `INCOPY.KEY` 不是一回事

`DBGMODE.key` 在固件中出现两次，字符串均为：

`/ATA1/DBGMODE.key`

调用的检查函数为 `0x200A51E0`，已还原为单纯的文件存在检查：

1. 只读打开文件；
2. 能打开就关闭并返回 `1`；
3. 打不开返回 `0`。

它不检查长度和内容。

但其调用仍受启动状态位控制：

- 状态位 `0x00100000` 对应调试模式参数 `2`；
- 状态位 `0x00080000` 对应调试模式参数 `1`。

另外，某内部结构的第 23 字节为 `0xFF` 时，也可以绕过文件存在检查。这很像工厂生产配置或内部启动标志。

`DBGMODE.key` 之后调用的 `0x2036D4E8(mode)` 会启动一长串设备、电源、通信和 UI 状态流程，不是简单把终端输出打开。

**风险判断：中高。** 虽然文件本身只检查存在，但没有满足启动状态位时可能完全无效；满足时则可能进入更新、工厂或下载模式。

## 三、配置备份/恢复的固定数据长度已确认

固件中有两条互补路径：

### 导出路径（推定函数 `0x200800AC`）

- 根据机身/模块和存储位置构造文件名；
- 创建输出文件；
- 从调整配置工作区写出固定长度数据；
- 固定写出长度：`0x0C5C = 3164` 字节；
- 写入长度不等于 3164 会记录 `config file write size error`。

### 导入/恢复路径（推定函数 `0x20080418`）

- 打开输入配置文件；
- 向配置工作区读取固定 `3164` 字节；
- 读取不足或超出均判失败；
- 后续再进入配置解析/应用流程。

因此 `CONFIG.TST/CONFIG.BAK` 不是文本设置文件，而是一个固定长度的二进制调整配置容器。

### 可见的命名规则

固件保留以下路径和模板：

- `/ATA1`
- `/IROM`
- `/ATA1/RADJ`
- `/IROM/RADJ`
- `/CONFIG.TST`
- `/CONFIG.BAK`
- `/CFGT`
- `/CFGB`
- `%s%s%04d.TST`
- `%s%s%04d.BAK`

所以生成文件很可能采用：

- `CFGTxxxx.TST`
- `CFGBxxxx.BAK`

其中 `xxxx` 来自内部序号或脚本编号。机身和模块还会根据当前控制对象选择 ATA1（SD 卡）或 IROM（内部文件系统）。

**这条路径最适合语言改区研究**：先只导出 3164 字节配置，不对内部闪存写入；之后再比较中文模块写入前后的差异。

## 四、配置系统属于维修脚本状态机

`CONFIG` 导出和恢复并非普通用户菜单代码，而是被维修状态机调用。相关状态函数会设置：

- 配置操作类型；
- 机身或模块目标；
- 文件序号；
- 完成后的状态跳转。

脚本系统同时支持：

- `adjcom`、`adjcom2` 调整命令；
- `install`、`uninstall` 维修脚本安装；
- `/SCINST.TST` 脚本安装入口；
- `/SCRIPT.*`、`/SCRP` 等脚本命名空间。

这说明官方维修工具很可能只是生成对应脚本/配置文件，再通过机身状态机执行，并不一定需要专用刷机程序。

## 五、模块通信函数已定位

之前看到的 `0x2036C624` 不是具体语言读取函数，而是一个薄封装，直接跳转到通用分派器 `0x20068388`。

该分派器按第一个参数选择 1～7 类操作，再从当前机身或模块的函数表调用对应回调。其参数模式大致为：

- 参数 1：操作类别/目标类型；
- 参数 2：命令或子类别；
- 参数 3：数据编号或参数。

语言附近的兼容性代码通过它读取多组项目：

- `(3,1,3)`
- `(6,1,3)`
- `(3,1,10)`
- `(2,2,10)`

随后比较机身和模块返回值。这部分已能确认是**模块兼容性/版本一致性检查**，暂时不能把编号 `10` 直接解释为语言字段。

## 六、`COMMAND.NS1` 是真正的命令文件解释器

路径：`/ATA1/COMMAND.NS1`

固件会：

1. 构造路径并打开文件；
2. 使用约 256 字节命令缓冲区逐条读取；
3. 根据首字符分派不同操作；
4. 可见的命令首字母包括 `V/v`、`W/w`、`X/x`、`U/u` 等；
5. 调用底层参数读取、写入或执行函数。

这与固件中的十六进制读写终端是一致的。它比 `CONFIG` 备份通道更底层，也更危险，不应作为第一实验入口。

## 七、当前安全优先级

### 可以优先研究

1. 找到只读“配置导出”状态的入口；
2. 导出 `3164` 字节的机身配置；
3. 对同一机身执行中文模块配置读取；
4. 再导出一次；
5. 进行二进制差分和校验定位。

### 暂时不要尝试

- 制作 16 字节 `INCOPY.KEY`；
- 空 `DBGMODE.key` 配合未知按键启动；
- 制作 `COMMAND.NS1`；
- 使用 `fe/fbe/me/mf/ex` 等写入或任意执行命令；
- 恢复来源不明的 `CONFIG.BAK`。

## 八、下一阶段目标

1. 从状态函数表中恢复配置备份菜单的按键入口；
2. 判断 `CONFIG.TST` 是否可通过 SD 卡根目录自动触发；
3. 还原 3164 字节配置的头部、项目表和校验；
4. 在主程序中追踪“当前语言编号”和“可用语言数量/掩码”的来源；
5. 识别调试串口初始化参数、UART 寄存器和可能的 PCB 测试点。
